# Две админки

В проекте две разные панели. Их код и способы публикации различаются.

| Панель | Где открывается | Исходники | Назначение |
| --- | --- | --- | --- |
| Серверная | `/admin` у Worker | `server/install-notifier/` | Пользователи, Premium, аналитика, поддержка, публикации, настройки |
| Редактор блога | `http://127.0.0.1:8930/admin` | `tools/blog_admin/` | Статьи, изображения, предпросмотр и деплой сайта |

## Серверная панель

`worker.js` содержит исторический HTML/JS-шаблон в экранированных строках.
Новые изменения интерфейса вносить через модули, не ручным патчем этих строк.
`admin_ui.js` — оболочка, `admin_theme.js` — визуальная система;
`users_ui.js`, `analytics_ui.js`, `ai_ui.js`, `publications_ui.js`,
`blog_ui.js`, `social_ui.js`, `threads_ui.js`, `tasks_ui.js`,
`economy_ui.js` — разделы.
Обработчики данных искать в соответствующих серверных модулях и маршрутах Worker.

Календарь блога Worker управляет датами и разрешением на публикацию: очередной
деплой сайта сначала синхронизирует его с источниками. HTML обновляется при
деплое, а не в момент сохранения даты в панели. Даты плана отображаются по МСК;
социальные очереди хранят время в UTC.
Доступ защищён секретом `ADMIN_PASSWORD`, пароля по умолчанию нет.
Ключ приложения административного доступа не даёт. Cookie отзывается
при смене пароля, живёт не более 7 дней и истекает после 12 часов
бездействия. Защита от перебора общая для формы и Bearer-пароля;
изменения с cookie требуют CSRF-токен.
Проверки и эксплуатация — [сервер](../server/README.md) и
[README воркера](../../server/install-notifier/README.md).

### Загрузка данных

Все разделы серверной панели используют `admin_data.js`: первый запрос показывает
скелетон, повторный переход — последнее успешное состояние; после 45 секунд
запускается обновление в фоне. Кнопка «Обновить» обходит срок кэша. Баланс Platega
обновляется с интервалом кэширования 15 секунд. Одинаковые одновременные запросы
объединяются, ключ включает фильтры и период. Формы, поиск и выбранные строки
сохраняются при фоновом обновлении. При ошибке остаются предыдущие данные и
доступна повторная загрузка; пустое состояние не подменяет сетевую ошибку.

Кэш пользовательских и финансовых записей живёт только в памяти вкладки
(до 32 ответов, 8 МиБ суммарно, 2 МиБ на ответ). После перезагрузки эти разделы
загружаются заново. Существующий снимок агрегатов аналитики в localStorage
исключает ленту событий и показывается только после проверки сессии.
Вход/выход и ответы 401/403 очищают кэш; после нового входа создаётся новая
страница без данных и черновиков предыдущей сессии. Запросы с изменениями
сбрасывают кэш до и после выполнения. Старые ответы не перезаписывают новые:
ожидающие загрузки повторяются после завершения записи. На сервере каждый
маршрут по-прежнему проверяет авторизацию.

`admin_reads.js` ограничивает параллельные чтения KV (8 одновременно) и делит
только текущую загрузку списка пользователей между одновременными запросами.
Экономика не использует серверный кэш денежных итогов. Аналитика сохраняет
прежний кэш сводки пользователей, изолированный по KV binding.

Проверки: `npm run test:admin:data`, `npm run test:admin:ui` (Playwright,
`NODE_PATH`, Chrome). Browser-тест использует изолированную базу, задержки и
ошибки ответов; рабочие данные и реальные публикации не затрагиваются.

### Видео

«Автопубликация → Сохранить» записывает площадки, время и активность канала.
Выбор соцсетей применяется к новым и ожидающим роликам этого канала;
индивидуальные даты сохраняются. Завершённые, публикующиеся и частично
опубликованные ролики автоматически не меняются. У каждого видео видны обе
площадки и их статусы. «Соцсети» в массовых действиях или в карточке ролика
меняет только его назначения, сохраняя успешные публикации при повторе.
В списке видео фильтр «Папка на Диске» выбирает исходную папку вместе с её
подпапками. «Выбрать все» выделяет все результаты фильтра и поиска, включая
ещё не раскрытые строки. Кнопка «Расставить даты» назначает даты ожидающим
роликам выбранной папки с учётом поиска; число роликов видно на кнопке,
интервал задаётся в диалоге. Без фильтров она обрабатывает всю очередь.
Для старых импортов папки обновляются кнопкой «Забрать с Диска» (или очередной
синхронизацией): сопоставление по ID файла сохраняет даты и историю публикаций.
Пока папка неизвестна, ролики доступны в пункте «Папка не определена».
Видео без даты только ожидают планирования: импорт с
Диска и время по умолчанию не разрешают автоматическую публикацию. Снятие даты
также останавливает автоматический выпуск ролика.

«Повторить» продолжает сохранённую загрузку. Если прежняя запись Instagram
недоступна, карточка предлагает «Новая публикация» с подтверждением: сервер
сначала проверяет старую запись и создаёт замену только при подтверждённом
отсутствии. История сохраняется, YouTube не повторяется. Потерянный ответ на
создание требует проверки; повторная загрузка автоматически не запускается.
«Убрать из списка» запоминает ID файла на Диске в исключениях, поэтому импорт
не возвращает удалённую строку. «Вернуть в очередь» сохраняет успехи площадок.

`SocialPublisher` сериализует публикации аккаунта и хранит подтверждённые
результаты загрузок отдельно от KV. При потерянном ответе загрузка автоматически
не повторяется; подтверждённый результат восстанавливается без новой отправки.
Импорт сравнивает контрольные суммы Диска: точная копия файла с другим ID или
именем не добавляется повторно. Разные версии с разным содержимым сохраняются.
Первый сбой автопостинга сразу отправляется в Telegram; одинаковая причина
одного аккаунта группируется на час, число повторов попадает в следующее
сообщение, если ошибка сохраняется. История в панели продолжает записываться.
Если Meta после 200 секунд всё ещё отвечает `IN_PROGRESS`, это ожидание,
а не ошибка: ролик остаётся в обработке, следующий крон продолжает тот же
контейнер. Сообщение об ошибке в Telegram при таком ожидании не отправляется.

Проверки: `npm run test:publications`, `npm run test:social:ui` (Playwright,
`NODE_PATH`, Chrome). `SOCIAL_UI_SCREENSHOTS=1` сохраняет снимки в
`output/social-ui/`. `node test-social-ui.mjs --serve` запускает изолированное
превью без рабочих токенов и публикаций в соцсети.

## Локальный редактор блога

Запуск из корня: `./scripts/blog_admin.sh`.
`server.py` — локальный сервер, `admin.html` — редактор,
`generator.py` — сборка страниц, `gen_images.py` — генерация иллюстраций.
Редактируется `web_landing/ru/blog/<slug>/source.json`;
`published: false` исключает статью из публичных индексов.
Кнопка публикации запускает деплой лендинга и IndexNow.
Источники и генерируемые файлы — [контент](../content/README.md).

### Замена очереди статей

Текст статей хранится в `source.json`, календарь и разрешение на публикацию —
в `blog_articles` в KV серверной панели. Перед каждым деплоем
`sync_worker_schedule.py` переносит даты и `published` из KV в известные
источники. Отсутствующая в KV статья переводится в черновики; её текст
сохраняется. Неизвестные серверные slug не создают страницы.
После этого генератор убирает будущие и отключённые статьи из HTML и индексов.
Удаление или перенос в панели отражается на сайте при следующем успешном
деплое (ежедневно в 09:00 МСК или вручную).

Публичный служебный `GET /api/blog/schedule` возвращает только
`{schema:1, complete:true, count:N, articles:[{slug,datePublished,published}]}`,
с `Cache-Control: no-store` и `X-Robots-Tag: noindex`. Текст, заголовки,
внутренние поля и секреты не передаются. Если KV недоступен, повреждён или
пока не создан, endpoint возвращает 503, не резервный каталог.
Синхронизатор проверяет версию, полноту, количество, уникальность slug и даты
до записи файлов; ошибка останавливает production-деплой до push.
Обычный локальный `generator.py regen` и предпросмотр работают офлайн.

Перед заменой сохранить актуальный KV в игнорируемый `output/`:

```bash
# Из server/install-notifier/; каталог output/ должен существовать.
npx wrangler kv key get blog_articles --binding INSTALLS --remote --text > ../../output/blog-catalog-before.json
```

После изменения источников собрать каталог из корня проекта:

```bash
python3 tools/blog_admin/build_worker_catalog.py --existing output/blog-catalog-before.json --catalog-json output/blog-catalog-next.json --write-module
```

Утилита сохраняет существующие записи с оставшимися источниками без изменений,
убирает записи без источников и добавляет метаданные новых статей. Она не пишет
в KV и не публикует сайт. Для обновления обложек существующих статей передать
`--refresh-media slug-1 slug-2`: обновятся только `cover` и `coverAlt`, а даты,
разрешение выпуска и прочие поля из панели сохранятся. Обложка разрешённой
будущей статьи доступна до выхода, чтобы панель показывала миниатюру; HTML,
учебные изображения и исходник до даты выхода не публикуются.
`server/install-notifier/blog_catalog.js` — резервный
каталог Worker, который используется при отсутствии KV и кнопкой сброса панели;
его нужно коммитить вместе с источниками и выпускать с Worker.

Проверенный `output/blog-catalog-next.json` загружается через
`npx wrangler kv key put blog_articles --binding INSTALLS --remote --path ../../output/blog-catalog-next.json`
из папки Worker. После записи перечитать значение и сравнить состав и даты.
Обычный деплой лендинга сам синхронизирует календарь и пересобирает страницы
и индексы. Видеоролики и Threads при такой замене не затрагиваются.

Проверки: `python3 -m unittest tools.blog_admin.test_worker_catalog tools.blog_admin.test_worker_schedule`,
`npm run test:publications` из папки Worker.

## Экономика

Проверенные API, ограничения точности и план импорта магазинных отчётов —
[финансовые источники](economy-data-sources.md).

`economy_admin.js` хранит параметры и ручные записи в `economy_config` (KV).
`economy_ui.js` показывает продажи, расходы, прибыль и компактное распределение;
основной список — единый журнал с поиском и фильтрами. В нём поступления
выделены зелёным, расходы — красным, выводы — синим, комиссии — янтарным;
типы различаются также иконкой и текстовой меткой. Положительная прибыль
показана на синем фоне, как в аналитике, а при включённых оценках магазинов
имеет подпись «Оценка после расходов». «+ Операция» добавляет
поступление, расход, вывод или отдельную комиссию. Реквизиты открываются по записи,
повторяющиеся и прошлые расходы доступны в свёрнутом реестре. Все даты — МСК.

- Подтверждённые СБП и ручные поступления СБП/«Другое» входят в продажи.
  Покупки App Store / Google Play / RuStore включены по тарифу и отмечены
  как оценка до комиссии магазина. Ручные выплаты магазинов справочные:
  повторно не увеличивают продажи. Тестовые покупки по умолчанию исключены;
  флажок их показа меняет только список, не расчёт.
- В свёрнутом блоке Platega доступны текущие балансы напрямую из
  `GET /balance/all` через admin-only `GET /api/admin/economy/platega`.
  Запрос выполняется при первом раскрытии и по кнопке обновления. Это остаток
  сейчас, отдельно от периода отчёта. Замороженные USDT показываются отдельно,
  без выдуманного вычитания из остатка; USDT не приравниваются к USD.
  Секреты остаются на сервере. При ошибке прошлые данные помечены как устаревшие,
  нулевой баланс не подставляется. Чтение не изменяет расчёты или хранилище.
  См. [официальную документацию](https://docs.platega.io/получение-балансов-33582950e0).
  Поля комиссии транзакции пока не используются: публичная схема не объясняет
  единицы `comission` и смысл `comissionType`; публичная история выводов
  не описана. Для них остаётся управляемый ручной учёт.
- Комиссия Platega — `paymentFeePercent`, по умолчанию **8%**. Считается
  отдельно с каждого включённого СБП-поступления с округлением до копеек.
  Не применяется к магазинам и выводам. `expenses.paymentFeesRub` входит
  в общие расходы; в журнале показана одна сумма комиссии за выбранный период.
- Выводы — `config.withdrawals`, API `withdrawals/add|update|delete`.
  Запись хранит сумму, валюту RUB/USD, дату, источник, комиссию и способ её
  удержания: `additional` — сверху (получено = сумма; списано = сумма + комиссия),
  `included` — из суммы (списано = сумма; получено = сумма − комиссия).
  Сам перевод не является новым доходом или расходом; прибыль уменьшает
  только комиссия (`expenses.withdrawalFeesRub`). Удаление/правка вывода
  сразу пересчитывает связанную комиссию без отдельной дублирующей записи.
- USD-поступления и выводы сохраняют свой `usdRate`: изменение общего курса
  не переоценивает уже внесённые операции. При добавлении поле заполняется
  текущим курсом из параметров; для точного учёта указывается курс операции.
  Старые рублёвые поступления `amountRub` продолжают поддерживаться.
- Расходы `extraExpenses` имеют категорию `expense` или `commission`, дату,
  валюту RUB/USD и повторение once/monthly/yearly. 29–31 числа сокращаются
  до конца месяца; дата окончания включительна. USD-расходы по прежней модели
  используют общий курс. Будущие/внепериодные расходы не засоряют журнал,
  но доступны для изменения в реестре расходов.
- Cloudflare и домен — бюджет по дням периода. Для фактических списаний
  отключить соответствующий бюджет в параметрах и добавить расход с датой.
  Стоимость ИИ накопительная: входит только во «Всё время»; в других периодах
  её величина доступна отдельно. «Всё время» начинает бюджет с первой известной
  записи, при пустой истории — с начала месяца.
- Фонд развития вычитается из положительной прибыли до распределения между
  партнёрами. Убыток не создаёт выплат. Доли и ставка платёжной комиссии
  применяются к выбранным историческим периодам; настройки не проводят
  реальных выплат. Журнал — управленческий расчёт, не баланс кошелька платёжки.

Проверки из `server/install-notifier/`: `npm run test:economy`,
`npm run test:economy:ui` (Playwright через `NODE_PATH` и Chrome;
браузер можно задать `CHROME_PATH`). Браузерный тест использует настоящий Worker
с изолированным KV и проверяет CRUD, комиссии, валюту, периоды, ошибки сохранения
и размеры 320/390/900/1440 px. `ECONOMY_UI_SCREENSHOTS=1` сохраняет снимки в
`output/economy-ui/`; `node test-economy-ui.mjs --serve` запускает локальное превью.

## Версии и использование режимов

В аналитике «Обновились за период» — уникальные зарегистрированные аккаунты,
у которых после исходного наблюдения подтверждено повышение версии Android/iOS.
История собирается с 19.10.2026, первый контакт задаёт исходную версию.
Новые аккаунты, повторные обращения и переход на старую версию не увеличивают
счётчик. Для двух устройств одной платформы хранится максимальная наблюдавшаяся
версия; обновление более старого устройства до уже известной версии не различимо.
Смена версии записывается вместе с обычным профилем, без дополнительных KV put.
Таблица версий — последняя известная мобильная платформа и версия аккаунта за
всё время, включая новые аккаунты, без гостей. Это не число скачиваний из стора.

Актуальные режимы обучения: «Билеты», «Темы», «Экзамен», «Марафон», «Лента».
Игры: «Живой город», «Это знак», «Регулировщик», «Перекрёсток», «Знаки»,
«Парковка». Исторические ключи переименованных игр сохранены, поэтому их
накопленная статистика продолжается. Ключ `roundabout` принимается для старых
очередей, но не выводится. «Нарушитель» пока недоступен в магазинных сборках.
Для «Марафона» и «Знаков» нужен выпуск приложения с новым учётом запусков.
Для регулировщика, перекрёстка и парковки учитываются сыгранные раунды
с хотя бы одним ответом после возврата из Godot.
Проверки: `npm run test:usage`, `npm run test:security`.

В «Аналитике» блок «Способы авторизации» показывает количество и долю
Яндекса, Google, Apple и Telegram от всех сохранённых аккаунтов выбранного
приложения за всё время (тот же знаменатель, что «Всего аккаунтов»).
Гости, suspect и pending исключены. Неизвестный провайдер показывается
отдельной строкой, чтобы не терять его долю. Период графиков на блок не влияет;
разные провайдеры одного человека считаются отдельными аккаунтами.
Данные `users.authProviders` рассчитываются из уже загруженных сводок KV,
дополнительных чтений или записей нет.


### Компоновка аналитики

Обзор текущих аккаунтов → активность и рост за период → использование
режимов → состав аудитории (вход и версии) → география новых аккаунтов →
источники сайта и первые запуски по магазинам. Авторизация и версии стоят
в одной строке на широком экране; география занимает всю ширину. На узком
экране карточки идут последовательно. Области «Сейчас», «Всё время» и
«За выбранный период» подписаны отдельно. Детали подсчёта — в подсказках;
история по дням раскрывается по запросу. Длинная таблица версий прокручивается
внутри карточки и доступна с клавиатуры.

Проверка: `npm run test:analytics:ui` (Playwright через `NODE_PATH`, Chrome).
`ANALYTICS_UI_SCREENSHOTS=1` сохраняет снимки в `output/analytics-layout/`;
`node test-analytics-layout-ui.mjs --serve` поднимает собранную админку
с изолированными тестовыми аккаунтами и событиями на localhost.

## Охват сообщений

В «Уведомлениях» у всех сообщений доступны «Увидели / Нажали» и CTR
(уникальные нажавшие / уникальные увидевшие): баннер и окно — показ и нажатие,
пуш — открытие, запись в списке — нажатие действия. Показ пуша на экране
блокировки приложению не виден и не считается. Один аккаунт считается один
раз на сообщение на всех устройствах; гости — по установке. Вход после
гостевого просмотра может дать две записи аудитории. Крестик не считается
кликом. Нажатие учитывается только для баннера с действием; оно также
подтверждает просмотр. Это попытка перехода, а не подтверждение загрузки сайта.

События поступают только из новых сборок приложения после добавления
измерения; история показов старых сборок не восстанавливается. Просмотр —
не менее половины загруженного баннера на экране около секунды, на открытой
главной странице активного приложения. Ошибка картинки и блок статистики
не считаются просмотром. Офлайн-события сохраняются на устройстве до 30 дней
(очередь до 500 событий) и отправляются при следующем обновлении сообщений.
Отключение баннера не отменяет уже произошедшие события, удаление прекращает
их приём. Админка показывает агрегаты с задержкой буфера статистики.

Маршрут `POST /api/notifications/events` требует ключ приложения, проверяет
кампанию и аудиторию. Идентификаторы дедупликации основаны на HMAC аккаунта
или установки; email в статистику не попадает. Все события проходят через
`trackStats` и `StatsBuffer`, счётчики `notice_metrics:<campaignId>` пишутся
в KV только пачками. Проверки: `node --test test-notice-metrics.mjs`,
`test/notice_view_observer_test.dart`, `test/notice_metrics_queue_test.dart`,
`test/remote_notifications_test.dart`,
`test/app_notice_banner_test.dart`.

Для удалённого ролика YouTube в ошибках есть «Новая публикация» рядом со
ссылкой проверки. После подтверждения сервер проверяет канал и прежний ID
через авторизованный YouTube API: доступная запись восстанавливает статус,
закрытая запись или ошибка API останавливают замену. При отсутствии записи
создаётся отдельная попытка с сохранением прежнего ID в истории; Instagram
не затрагивается. Потерянный ответ загрузки блокирует повтор этой попытки.
Обычный ручной повтор уже успешной площадки сохраняет её статус и ничего
не загружает.
Если аккаунт занят незавершённой задачей, запуск замены YouTube сразу отвечает
409 с `retryAt` и временем МСК; фоновая загрузка в этом случае не создаётся.

Назначенная повторно публикация со старым ID проверяется автоматически в своё
время: доступный ролик восстанавливает статус, подтверждённо недоступный получает
новую попытку с сохранением истории. Это действует для незавершённой записи с
явной наступившей датой; уже опубликованные ролики не переотправляются. Неизвестный
результат отправки и ошибки доступа остаются на проверке. Обрыв YouTube с
сохранённой сессией отображается как продолжающаяся обработка и возобновляется
автоматически. Рабочие статусы читаются из SQLite, без задержки KV-проекции.

### Быстрое открытие аналитики

Последний полный результат сохраняется в браузере отдельно для приложения и
периода на срок до 7 дней. После быстрой проверки сессии панель сразу показывает
сохранённые значения с датой и временем по МСК, затем обновляет их в фоне.
В кнопке обновления вращается иконка; повторный запрос того же периода во время
загрузки не запускается. При смене периода предыдущий запрос отменяется.
При ошибке сохранённые данные остаются с предупреждением. Выход или истечение
сессии очищает кэш. Лента отдельных событий в кэш не сохраняется.
Первое открытие без сохранённых данных требует загрузки с сервера. Чтение дней
на сервере выполняется параллельно, максимум по 8 запросов к KV одновременно.
Проверки: `npm run test:analytics:ui`, `npm run test:usage`, `npm run test:security`.


Локальные редакторы проверяют Host и Origin, а для POST требуют случайный
`X-Local-Token`. Браузер получает его с `/api/local-session`; загрузчик
`/local-security.js` добавляется в HTML до скриптов редактора. Для локальных
CLI-запросов сначала получить токен через GET и передавать его заголовком.
Обложки блога допускают только проверенные растровые PNG/JPEG/WebP/GIF;
HTML/SVG и выход за корень раздачи отклоняются. Проверки:
`python3 -m unittest tools.test_local_http_security tools.test_web_security`.

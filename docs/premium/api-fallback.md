# Запасной адрес сервера (api.pdd-drive.app)

Основной адрес воркера — `pdd-install-notifier.sergei-pdd.workers.dev`. У части
операторов он нестабилен: вход заканчивается ошибкой «нет связи с сервером», а
отчёты об ошибках тоже не доходят (они идут туда же). Запасной адрес —
**тот же воркер** на отдельном домене `api.pdd-drive.app`.

Адрес `workers.dev` остаётся основным и никуда не делся: на нём настроены колбэк
Platega (`/api/pay/platega/callback`), магазины и все старые версии приложения.
Запасной адрес только добавлен рядом.

## Как устроено

- Домен `pdd-drive.app` куплен в Cloudflare (тот же аккаунт, что и воркер).
  Поддомен `api` подключён к воркеру `pdd-install-notifier` как Custom Domain
  (Workers & Pages → pdd-install-notifier → Domains → Add Domain). Код воркера
  при этом не менялся и не деплоился.
- В приложении: `BackendConfig.notifierHosts` = основной + запасной
  (`INSTALL_NOTIFY_FALLBACK_URL`). Запасной подключается только к боевому воркеру.
- Вход (`/api/auth/session`): три попытки по очереди — основной, запасной,
  основной (8 + 8 + 10 с). В 2.2.5+66 ответ сервера не повторяется. `sendWithRetry` в
  `lib/data/services/network_retry.dart`; адрес, который сработал, пробуется первым.
  В подготовленном после релиза клиенте выдача сессии также может повторить
  500/502/503/504, если Retry-After позволяет уложиться в ограниченное ожидание
  (не более двух секунд между попытками). Это не распространяется на обычный POST.
- В подготовленном 27.10 клиенте Telegram перед единственным POST `/request`
  выбирает доступный адрес через безопасный GET `/api/pay/status`. Статус
  оплаты `available=false` не мешает входу. Опрос `/check` использует адрес,
  принявший challenge; эти POST автоматически не переотправляются, поскольку
  `/request` настраивает вебхук, а `/check` потребляет одноразовое подтверждение.
  После неопределённого ответа предлагается новая явная попытка входа.
  Старые магазинные версии 65/67 используют только основной адрес Telegram.
- Отчёты об ошибках (`/api/diagnostics`) пробуют основной, затем запасной.
- В релизе 2.2.5+66 (`dfe6028a`) GET и идемпотентные POST через `NotifierApi`
  тоже используют оба адреса при сетевом отказе; снимок прогресса — две попытки
  по 15 секунд. Неидемпотентный POST (например, создание оплаты) идёт один раз
  на адрес, который последним сработал. Обычный HTTP 503 синхронизации
  возвращается вызывающему коду, а не включает переключение адреса.
- Сообщения в Telegram: `timeout:3x` — три попытки не помогли; «Вход удался не
  сразу» (`auth.recovered`) с кодом `retry_ok:2x` (помог повтор) или
  `fallback_ok:2x` (помог запасной адрес — основной недоступен части людей).

## Проверка

```bash
curl https://api.pdd-drive.app/api/pay/status            # то же, что у основного
curl -X POST https://api.pdd-drive.app/api/pay/platega/callback -d '{}'   # 401
```

## Ограничения

- Оба адреса обслуживает Cloudflare. Запасной адрес
  помогает, если оператор фильтрует имя `*.workers.dev`; если он режет саму
  сеть Cloudflare, нужен путь вне Cloudflare (например,
  пересылающая функция в Yandex Cloud) — отдельная задача.
- Запасной адрес получит только версия приложения, собранная после этого
  изменения.
- Этот документ описывает код 2.2.5+66 и последующие изменения транспорта.
  Поведение более старых опубликованных версий нужно проверять по их SHA.
  Оба адреса по-прежнему используют один backend; это не независимые реплики.
- Домен `pdd-drive.ru` остаётся на серверах имён reg.ru и в Cloudflare не
  переносился (reg.ru требует идентификацию через Госуслуги для смены DNS).
  Зона `pdd-drive.ru` в Cloudflare в статусе pending — её можно удалить.

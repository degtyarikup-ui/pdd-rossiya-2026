# AccountState: безопасный выпуск серверных изменений 18.10.2026

## Что меняется

`AccountState` — основной источник профиля, прогресса, поколений/отзыва сессий,
платёжных заказов и отдельного `payment_ledger`. Все маршруты пользователя,
админские изменения пользователя, вход и платёжные колбэки сериализованы по
`userId` в глобально адресуемом Durable Object. Изменения документов одного
запроса фиксируются одной транзакцией. Одновременные IAP, СБП, синхронизация и
выдача админом больше не перезаписывают чужой Premium устаревшим профилем.

KV становится проекцией для списков и аналитики. Неудачная проекция повторяется
через durable outbox и alarm; успешная оплата не зависит от доступности KV.
Уведомления Telegram и аналитика после транзакции также сохраняются в outbox.
Крупный прогресс делится на части ниже лимита одного значения DO. Документы с
`expiration`/`expirationTtl` имеют абсолютный `expiresAt`, проверяемый при чтении,
и удаляются alarm. Recovery alarm сохраняется до primary commit, поэтому
падение процесса между commit и первой отправкой не оставляет тихий аккаунт
с навсегда забытым outbox. Админские и OAuth state/session записи, находящиеся вне
аккаунтных префиксов, продолжают использовать KV TTL. Поколения сессий,
тумбстоуны удаления и финансовый журнал намеренно не имеют TTL.

Первое чтение существующего документа импортирует его из KV. Затем авторитетен
DO, а не KV. Существующие сессии не требуют массового выхода. Удаление аккаунта
создаёт тумбстоун и меняет поколение сессии; старый токен и поздняя оплата не
восстанавливают профиль. Состояние удалённого заказа, оплаченного позднее, —
`requires_refund`; его нужно разобрать с провайдером.

## СБП и восстановление

Перед внешним POST создания платежа сервер сохраняет резерв заказа и связь
заказ → аккаунт в DO. При потере ответа повторный запрос не создаёт второй
платёж автоматически. Колбэк с `payload` либо статус, перечитанный по `txId`,
восстанавливает связь. Статус, сумма, валюта и для восстановления `payload`
проверяются через аутентифицированный API Platega; параметры клиента не дают
Premium. Отдельный журнал и начисление срока фиксируются одной транзакцией.
Повторная доставка не начисляет срок второй раз.

Platega не документирует идемпотентность создания через клиентский ключ.
Сервер не повторяет неоднозначный POST. Если провайдер создал платёж, но ответ
потерялся и колбэк не пришёл, после 20 минут заказ получает
`creation_unknown`: его сверяют в кабинете по `payload`. Такой заказ блокирует
новый POST независимо от возраста; повторы возвращают 409 с номером заказа.
Это внешний неатомарный участок, который нельзя превратить в распределённую
транзакцию локальным mutex. Резерв и журнал сохраняют данные для сверки.

Операционная сверка `creation_unknown`:

1. Найти `order` из ответа 409/сохранённого intent и его `payload` в кабинете
   Platega; получить фактический provider transaction ID. Не угадывать статус.
2. Из защищённого админского клиента вызвать
   `POST /api/admin/users/reconcile-payment` с admin Bearer и JSON
   `{userId, order, txId}`. Значения секретов в команды/логи/документы не помещать.
   Endpoint работает в canonical AccountState, требует точное совпадение
   перечитанного у Platega `payload` с `order`, проверяет сумму/валюту и повторно
   перечитывает статус. Произвольный объявленный статус в JSON не принимается.
   Ответ `{ok:true, order, status}`; подтверждённый заказ начисляется один раз,
   проверенный CANCELED/FAILED снимает блок. Если провайдер возвращает PENDING,
   резерв остаётся creation_unknown и новый POST по-прежнему запрещён до
   проверенного подтверждения/отмены; повторить сверку после изменения статуса.
3. Альтернатива — повторная доставка исходного provider webhook из кабинета:
   существующий защищённый callback тоже перечитывает статус и восстанавливает
   связь. Нельзя вручную редактировать KV — это проекция, а не основной документ.
4. Если провайдер не находит transaction, сохранить блок и обратиться в его
   поддержку. API принудительного снятия без доказанного результата нет;
   отсутствие callback само по себе не доказывает отсутствие списания.

Крон каждые пять минут обходит ограниченное число заказов и профилей с курсором
(по 25). Это восстановление и повторная проверка, а не обещание перечитать все
подписки за пять минут. Исторический `confirmed` без журнала восстанавливает
срок от исходного `confirmedAt`, а не от сегодняшней даты. Неоднозначное
наложение старых начислений требует ручной сверки.

## Обязательный порядок деплоя

1. Сохранить номер текущей версии Worker, SHA исходников и доступную резервную
   копию KV. Сверить действующие секреты по **именам**, не печатать значения.
2. Проверить `npm run test:security`, все `node --test test-*.mjs` и
   `npx wrangler deploy --dry-run`. Проверить новые девять DO bindings, включая
   `ACCOUNTS`/`AI_QUOTAS`, и миграцию `v7-accounts-and-ai-quotas`.
3. Деплоить Worker **с** этой миграцией и `ACCOUNT_STATE_REQUIRED=true`.
   Без binding доступ к аккаунтным операциям закрывается с 503. Не включать
   старый KV путь в production ради обхода ошибки конфигурации.
4. На отдельном тестовом аккаунте проверить вход, прогресс, выход/повторный
   вход, удаление и отказ старого токена. Провести sandbox/TestFlight/Play
   license test покупки, восстановление после перезапуска и две параллельные
   оплаты; подтвердить один ledger на заказ и отсутствие переноса владельца.
5. Настроить callbacks ниже и проверить реальную тестовую доставку. Проверить
   живые alarms/outbox/логи без секретов и сверку одного незавершённого заказа.
6. Выпустить согласованный клиент. Старые объяснения ИИ имеют временную
   совместимость до указанной даты ниже; старый свободный чат требует обновления.

### Условия, без которых деплоить нельзя

- **`GOOGLE_ANDROID_CLIENT_IDS`** (на 18.10 в production его нет). Новый
  сервер проверяет `aud/azp` access-токена Google без исключений, а все
  вышедшие Android-сборки входят именно так. Без секрета вход через Google на
  Android перестанет работать у всех. Значение — через запятую все Android
  OAuth client ID из Google Cloud → APIs & Services → Credentials для
  `ru.pdd.pdd_app` (SHA-1 подписи Google Play и upload-ключа) и `ru.pdd.pdd_app.dev`.
  `npx wrangler secret put GOOGLE_ANDROID_CLIENT_IDS`.
  На 18.10 в production заданы два клиента: `505681869803-bdnp…` (проект «My Project 2910»)
  и `92147521898-5u7h…` — именно им выдаёт токены сборка из Google Play (найден по логу
  `google access token client rejected`; в консолях проектов, которые видел владелец, его нет).
  Отклонённый клиент пишется в лог воркера: `npx wrangler tail --search "client rejected"`.
- **`APPLE_LEGACY_CLAIMS_UNTIL`** (в `wrangler.toml`, 2027-01-31). Сборки iOS до
  2.2.4 не передают `appAccountToken`; до этой даты их новая покупка
  привязывается к первому заявителю, как в текущем production. Без переходного
  окна каждая новая покупка со старого iPhone получала бы 409 без Премиума.
  Дату не ставить раньше, чем почти все iOS-пользователи обновятся.
- Сервер выкладывается **раньше** клиента 2.2.4: новая iOS-сборка не открывает
  покупку без `/api/user/store/account-token`.

### Точная процедура (по шагам, с подтверждением владельца)

```bash
cd server/install-notifier
npx wrangler deployments list | head -8          # записать текущую версию (на 18.10: cfd387b0)
npx wrangler secret list                          # только имена
npx wrangler kv key list --binding INSTALLS --prefix user: > ../../output/kv-users-$(date +%F).json
# резервная копия профилей/заказов: значения user:, pay_order:, payment_ledger:,
# pay_tx:, user_progress: выгрузить скриптом в output/ (в git не класть)
node --test test-*.mjs && npx wrangler deploy --dry-run
npx wrangler deploy                               # только после «да» владельца
```

Сразу после деплоя: вход Google на старой Android-сборке из Play, вход Apple и
Яндекс, `/api/user/status` у аккаунта с действующим Премиумом (тот же срок, что
в бэкапе), одна тестовая СБП 99 ₽ на служебном аккаунте, восстановление покупки
на iPhone. Ошибки в Telegram-топике «Ошибки» — смотреть 30 минут.

### Откат

KV остаётся проекцией DO и обновляется после каждой записи, поэтому старый
Worker после отката видит актуальные профили:
`npx wrangler rollback <прежняя версия>`. Durable Object и миграцию v7 не
удалять. Пока работает старый Worker, он пишет только в KV. **Перед повторным
деплоем новой версии** поднять `ACCOUNT_STATE_EPOCH` в `wrangler.toml` на 1:
тогда AccountState заново импортирует профили, заказы и журнал из KV и не
затрёт оплаты, прошедшие во время отката (тест `test-release-handoff.mjs`).
Сохраняются только приватные Apple-токены отзыва (их нет в KV). Без смены
эпохи повторный деплой после отката запрещён.

## Авторизация и привязка магазина

Google ID token всегда проверяется по подписанным `aud`/issuer/expiry. Новый
Android-клиент запрашивает ID token через Web `serverClientId`; существующий
`GOOGLE_CLIENT_IDS` должен содержать этот Web client ID. Отсутствие
`GOOGLE_ANDROID_CLIENT_IDS` само по себе не мешает новому пути. Для старого
Android access-token входа нужны точные Android OAuth client IDs в
`GOOGLE_ANDROID_CLIENT_IDS`; пустой allowlist не открывает доступ любому приложению.
Проверить обе сборки в соответствующих кабинетах до выкладки.

`GET /api/user/store/account-token` с Bearer возвращает
`{ok:true, accountToken:<UUID>}`. UUID стабилен для серверного аккаунта и
передаётся в Apple `appAccountToken`. Проверяется значение из транзакции,
перечитанной у Apple. Legacy чек без UUID можно восстановить только за уже
подтверждённым владельцем; первый неоднозначный claim получает 409
`legacy purchase owner required` и требует проверки поддержкой. Подписки двух
сторов имеют отдельные ссылки и даты проверки. Проверка одного стора не
отменяет действующий Premium другого источника.

## ИИ: серверные квоты и совместимость

Для начального объяснения нужен ключ приложения; для свободного чата также
нужна сессия. Квоты резервируются атомарно в `AI_QUOTAS`: гость 3/день,
авторизованный бесплатный аккаунт 10/день, Premium 200/день; гостевой IP —
10/день, короткий лимит — 3/мин для гостя и 10/мин для вошедшего. Общий предел
по умолчанию `AI_GLOBAL_DAILY_LIMIT=5000`. Реальные расходы и число отказов
проверить после выпуска; это лимит защиты, не финансовая гарантия бюджета.

`GET /api/ai/status?installationId=...` и успешный ответ возвращают
`remaining`, `limit`, `resetsAt`; 429 дополнительно возвращает `reason` и
`retryAfterSeconds`. При минутном/общем ограничении дневной остаток не обнуляется.
Для `ru/en/kk` используется язык запроса. При отказе модели начальный ответ
может вернуть только официальный комментарий с `generated:false` и
`aiUnavailable:true`; свободный чат возвращает 503, без выдуманных правил.

В `wrangler.toml` уже включены `AI_LEGACY_EXPLANATIONS=true` и
`AI_LEGACY_UNTIL=2026-11-18T00:00:00Z`: старый клиент без installationId получает
ограниченные начальные объяснения по хешу IP+UA при действительном ключе
приложения, с теми же глобальными/IP ограничениями. После даты режим
автоматически закрывается. Старый свободный чат без сессии получает 401 и
требует обновления; это осознанное ограничение совместимости.

## Apple: удаление и уведомления

Новые секреты Sign in with Apple: `APPLE_AUTH_TEAM_ID`, `APPLE_AUTH_KEY_ID`,
`APPLE_AUTH_PRIVATE_KEY`. Это **отдельная** настройка от
`APPLE_IAP_ISSUER_ID`/`APPLE_IAP_KEY_ID`/`APPLE_IAP_PRIVATE_KEY`.
`authorizationCode` клиента обменивается на token и хранится только в DO,
без проекции в KV и без выдачи в профиль/админку. Удаление вызывает Apple
`/auth/revoke` и удаляет retained token после успешного отзыва. При временном
отказе Apple локальное удаление завершается с `appleRevocation:pending`:
refresh token переносится в приватный durable outbox той же транзакции.
Alarm, сохранённый до commit, повторяет REST revoke после перезапуска; после
успеха job и token удаляются. В KV, профиль и публичный ответ token не попадает.
Если старый аккаунт не имеет retained токена либо секретов нет, удаление
завершается с `appleRevocation:manual_required` и `appleManageUrl` для ручного
отзыва. Обязательного повторного входа для legacy нет: TN3194 допускает этот
случай, если token раньше не сохранялся. Клиент различает pending и manual.
Для полного автоматического сценария настроить
ключ и подтвердить login → delete → Apple credential revoked на устройстве.
Финансовые записи/тумбстоуны сохраняются для сверки; исторические записи
аналитики/поддержки требуют отдельной политики хранения, это не полный DSR-аудит.

Google RTDN: `/api/store/google/notifications`, секреты/vars
`GOOGLE_RTDN_AUDIENCE` и `GOOGLE_RTDN_SERVICE_ACCOUNT_EMAIL`, Pub/Sub push с OIDC.
Проверяются подпись Google, issuer, audience, подтверждённый email и точный
service account email. Затем актуальный статус покупки перечитывается у Google.

Apple: админский `GET /api/admin/store-webhooks` возвращает приватный URL
`/api/store/apple/notifications?token=...`. Настроить его в App Store Connect,
не копировать токен в отчёт/логи. MAC URL защищает callback; содержимое JWS
используется только как подсказка originalTransactionId, **не** как доверенный
статус. Итог перечитывается через App Store Server API и проверяются
bundle/product/claim/owner UUID. Это не проверка цепочки x5c подписи JWS.
Неизвестная ещё не привязанная покупка возвращает 503 для повторной доставки;
удалённый аккаунт подтверждается без воскрешения.

Адресные push используют HMAC topic `pdd_account_<64 hex>` от серверного
аккаунта и `SESSION_SECRET`; query email/userId больше не выбирает получателя.
Пересоздать старые адресные кампании, чтобы получить защищённый topic; старые
адресные push закрываются безопасно. Общие кампании сохраняют прежний контракт.

Production миграция/alarms и реальные тестовые IAP/СБП; магазинные OAuth IDs;

# Отдельная веб-страница оплаты СБП

Адрес: `https://pdd-drive.app/app/?checkout=sbp`.
Выбор тарифа в ссылке: `&tier=weekly` или `&tier=threeMonths`.
При неизвестном тарифе выбирается 90 дней. Из нативных iOS/Android экран
не открывается: правила магазина/региона остаются в `payment_mode.dart`.
Кнопки `/tarify/` ведут сразу на этот экран с выбранным тарифом.

## Сценарий

1. Шапка с иконкой и названием приложения. «Премиум доступ» и три кратких
   шага. До входа тарифы, почта платежа и кнопка оплаты скрыты.
2. Вход через общую форму `AuthModalSheet(embedded: true)` с существующими
   Google, Яндекс, Apple и Telegram. Browser и native имеют разные сессии.
3. Перед оплатой видны имя, почта и провайдер. Нужно явно подтвердить,
   что этот аккаунт используется в приложении. Смена аккаунта сбрасывает
   подтверждение, почту, запросы и результат предыдущего владельца.
4. Общие карточки `PremiumPlanCard`: 99 ₽ / 7 дней, 290 ₽ / 90 дней.
   Разовый платёж без автопродления. При действующем Premium показано,
   что срок добавляется после него; подписки сторов продолжаются отдельно.
5. Почта платежа передаётся как `metadata.user_email`, серверный аккаунт —
   `metadata.userId`. Почта не выбирает и не объединяет аккаунты.
6. Платёж открывается в той же вкладке. Возврат — на фиксированный origin
   `/app/?checkout=sbp&tier=…&pay=done|failed&order=…`. Клиент не может
   передать произвольный return URL. Старый `.ru` сохраняет свой origin.
7. Любой результат возврата перепроверяется сервером, включая `failed`.
   Оплата подтверждена только при серверном `confirmed`; query не выдаёт доступ.
8. После подтверждения видны срок доступа и инструкция открыть приложение
   с тем же аккаунтом. Нативное приложение уже перечитывает `/api/user/status`
   при возврате в foreground. Автоматическое открытие приложения не обещается:
   универсальные платёжные ссылки пока не зарегистрированы в мобильных сборках.

## OAuth и восстановление

`startWebOAuth` сохраняет выбранный тариф в исходной sessionStorage-записи
вместе со state/nonce на прежние 10 минут. `validateWebOAuthReturn` возвращает
`checkout_tier` только из этой записи после проверки state/provider/возраста.
Параметр callback с тем же именем удаляется. Произвольные redirect URL не
сохраняются. Обычный вход продолжает вести в профиль.

`POST /api/user/pay-check {current:true}` ищет последний незавершённый заказ
по `pay_intent:<authenticated user.id>` в AccountState, включая после потери
локального хранилища или перехода в другой браузер. Завершённые старые заказы
дают `status: none`, чтобы не мешать будущему продлению. Проверка конкретного
заказа по-прежнему требует его владельца. Ответ включает `order`, а при
`pending` — прежнюю HTTPS-ссылку на оплату. Статус проверяется у Platega.

При новом `pay-intent` с `checkout: sbp` существующий `pending` заказ
переиспользуется даже при другом тарифе/почте из второй вкладки. После
подтверждения/отмены возможна новая покупка. Неопределённое создание не
повторяется автоматически: прежний резерв и ручная сверка сохраняются.
Сетевой отказ создания фиксирует исходный выбор для явного повторного
запроса; отказ восстановления блокирует новую покупку до проверки.

Экран делает до 12 проверок (сначала каждые 5, затем 15 секунд), останавливает
таймер в фоне и оставляет кнопку ручной проверки. При смене аккаунта поздние
ответы не меняют новый экран. Секреты/credentials не появляются в query,
аналитике или checkout storage.

## Проверки

- `flutter analyze`, `flutter test`.
- `test/web_checkout_route_test.dart`: маршрут и провайдеры, отмена,
  подмена callback, допустимые номера заказов.
- `test/web_checkout_screen_test.dart`: подтверждение аккаунта, двойное
  нажатие, восстановление без prefs, неавторитетный failed redirect,
  поздний ответ другого аккаунта, переход авторизация → профиль/тарифы,
  скрытие тарифов после выхода, 320 px и шрифт 200% на ru/en/kk.
- `server/install-notifier/test-payments.mjs`: metadata, фиксированные
  возвраты, старые Android/web-контракты, поиск текущего заказа,
  другой аккаунт, переиспользование платежа второй вкладкой.
- `test-account-state.mjs`: восстановление из первичного DO после restart
  при отсутствующей KV-проекции intent.
- `npm run test:security`, `npm test`, `node --test test-*.mjs`.

Сервер выкладывается раньше нового веб-клиента: старый сервер не знает
`current:true`. Для отката сохранять AccountState authority и миграции.
Новых bindings, секретов или изменений формата аккаунта нет.

## Что проверять с владельцем на реальной оплате

Вход во все четыре существующих аккаунта на целевых устройствах, включая
Apple со скрытой почтой; подтверждение СБП в банке, callback, статус Premium
в приложении; выдача/доставка фискального чека. Автотесты и наличие API-ключей
не подтверждают эти внешние результаты. Страница не обещает отправку чека
на основании одного лишь заполнения email: фискализация требует отдельно
подключённого процесса продавца/провайдера.

Контракт `metadata.user_email`: [Platega, создание платежа](https://docs.platega.io/создание-платежной-ссылки-с-заданным-методом-29203843e0),
проверен 05.11.2026 (документ обновлён 04.11.2026).

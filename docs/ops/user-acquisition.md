# Источники пользователей и конверсия в Premium

Обновлено 25.10.2026. Описывает код текущего изменения; публикация сервера,
сайта и сборок приложения выполняется отдельно.

## Что измеряется

Система сохраняет первый известный источник браузера/установки, затем
прикрепляет его к аккаунту при синхронизации профиля. Сервер сохраняет этот
источник целым снимком: последующие входы, устройства и кампании не подменяют
его источник, статью или кампанию. `direct` также считается известным первым
источником. Запись `unknown` можно дополнить первым полученным снимком.

Это **первый сохранённый источник**, а не доказательство первоначального
привлечения за всю историю. У старого аккаунта источник может появиться после
обновления приложения или следующего входа. Потерянные старые метки не
восстанавливаются по IP, стране устройства, магазину установки или имени
провайдера входа. Отсутствующий Referer может означать прямой переход,
ограничение браузера или немеченую ссылку из другого приложения.

`installStore` и `marketingSource` независимы. Например, Google Play — магазин,
а Яндекс → статья — путь привлечения. Apple ID, Google и Яндекс остаются
отдельными аккаунтами; отчёт считает аккаунты, а не уникальных людей.

## Сохраняемые поля

| Поле | Назначение и ограничение |
| --- | --- |
| `marketingSource` | Нормализованный источник из разрешённого списка; иначе `unknown` |
| `marketingCampaign` | `utm_campaign`, до 64 символов `A–Z`, `a–z`, цифр, `.`, `_`, `-` |
| `marketingMedium` | `utm_medium`: например `organic`, `social`, `paid_social`, `referral`, `direct` |
| `marketingContent` | `utm_content`, например идентификатор ролика или варианта кнопки; тот же формат токена |
| `landingPage` | Путь первой страницы, до 240 символов; без query, fragment и полного URL |
| `referrerHost` | Только hostname сайта-источника, до 160 символов |
| `attributionMethod` | `web_utm`, `web_referrer`, `play_referrer`, `play_organic`, `rustore_referrer` |
| `installStore` | App Store / Google Play / RuStore / TestFlight / Web; отдельно от источника привлечения |

Источники: Threads, Instagram, YouTube, TikTok, Telegram, VK, Яндекс, Google,
Bing, DuckDuckGo, ChatGPT, Perplexity, Copilot, Gemini, Claude, прямой переход,
другой сайт, органика Google Play и неизвестный источник. Похожие домены
(`google.com.example.org`) не распознаются как поисковики. Домены OAuth
(`accounts.google.com`, `oauth.yandex.ru`, `id.yandex.ru`, `appleid.apple.com`)
не считаются поисковым привлечением.

## Переходы сайта, статей и приложения

Общий `web_landing/ru/assets/tracker.js` подключён к лендингу, генератору блога,
страницам теста знаний, тарифов и статическим `/go/*/`. Он сохраняет снимок в
`localStorage.pdd_acquisition_v2` и резервно в `sessionStorage` с тем же ключом.
Веб-приложение читает тот же ключ перед анализом текущего URL/Referer.
Предыдущая запись приложения `acquisition_v1` сохраняет приоритет своего
первого известного источника. Старый сессионный `pdd_attr_v1` мигрирует при
наличии корректной записи; отсутствующая историческая статья не придумывается.

Переходы на `/app/` получают UTM и `landing_page`/`referrer_host`; существующие
параметры режима и fragment ссылки сохраняются. Google Play получает эти поля
в `referrer`, RuStore — в `referrerId`. Статические редиректы `/go/web/`,
`/go/gplay/`, `/go/appstore/`, `/go/rustore/` используют тот же код.
Подготавливаются и статические, и динамически вставленные ссылки. Клики мышью,
клавиатурой и средней кнопкой сохраняют атрибуцию.

Например, человек пришёл из Яндекса на `/blog/entry/`, затем открыл другую
статью и нажал «Перейти к подготовке». В аккаунте останется первая статья
`/blog/entry/`. Событие нажатия отдельно содержит `path` той статьи, где нажали
кнопку. Таким образом первая статья привлечения и место клика не смешиваются.

Для публикаций использовать постоянный источник и разные кампании/материалы:

```text
https://pdd-drive.ru/links/?utm_source=threads&utm_medium=social&utm_campaign=autumn_2026&utm_content=reel_042
```

Поисковые посещения статей определяются по hostname Referer автоматически.
Явная ссылка `utm_source=google` без `utm_medium=organic` сама по себе не
доказывает органический поиск. Если браузер скрывает Referer и в ссылке нет
метки, система не назначает предполагаемый Threads/Instagram/поисковик.

`InstallReporter.clientMetadata()` добавляет снимок к существующей отправке
установки и синхронизации аккаунта; отдельный обязательный запрос для входа
не вводится. Веб-OAuth сохраняет первый снимок до перехода к провайдеру,
поэтому возвращение со страницы авторизации не подменяет источник.

## Магазины: индивидуальные данные и сводные отчёты

### Google Play

Нативный Install Referrer читает метки только при подтверждённом установщике
Google Play. Явная пара `utm_source=google-play&utm_medium=organic` сохраняется
как `google_play_organic` с методом `play_organic`. Она не называется «поиском»:
устройство не даёт надёжно разделить поиск и рекомендации магазина. Пустой
или недоступный referrer не превращается в органику.

Google описывает получение строки referrer и доступность данных до 90 дней
после установки: [Play Install Referrer](https://developer.android.com/google/play/installreferrer/library).
Разделение Search / Explore находится в сводных отчётах
[Play Console](https://support.google.com/googleplay/android-developer/answer/9859173).
Это другая единица измерения, которую нельзя приписать конкретному аккаунту
по совпадению даты или IP.

### RuStore

Ссылки получают `referrerId`; сборка `STORE=rustore` читает RuStore Install
Referrer SDK и проверяет `isFromRuStore`. Разрешённые поля очищаются ещё в
нативном мосте и сохраняются локально, чтобы не потерять их при одноразовой
выдаче магазином; полный исходный referrer в этот кеш не записывается. Отсутствие метки не
доказывает поиск внутри RuStore. Формат и API описаны в
[документации RuStore](https://www.rustore.ru/help/sdk/install-referrer/kotlin/10-6-1).

### App Store

Обычная ссылка сайта не передаёт приложению индивидуальный отложенный UTM
после установки. Источник App Store Search / Browse, переходы с сайтов и
привязанные к ним продажи доступны сводно в
[App Store Connect Analytics](https://developer.apple.com/help/app-store-connect-analytics/acquisition/acquisition/).
Нельзя превратить эту сводку в источник конкретного Apple-аккаунта приложения.
Если источник уже записан в том же аккаунте через веб, сервер его сохраняет
и после входа в iOS.

Код сохраняет существующий `pt` ссылки и добавляет `ct` кампании. Для
полноценных кампаний Apple нужны **оба** токена: реальный `pt` разработчика
получается генератором ссылок App Store Connect, его нельзя выдумать.
Одного `ct` в текущих исходных ссылках недостаточно для обещания, что кампания
появится в отчёте. Apple также применяет пороги приватности:
[правила campaign links](https://developer.apple.com/help/app-store-connect-analytics/acquisition/campaign-links).

**Автоматического импорта сводных Search / Explore / Browse из кабинетов
магазинов в текущую админку нет.** Таблица аккаунтов показывает только
сохранённые индивидуальные источники и явную категорию «Не определён».
Это ограничение нельзя устранить переименованием неизвестных установок в поиск.

## Как читать админку

В «Пользователях» источник виден у аккаунта, участвует в поиске и выгружается
в CSV вместе с кампанией, каналом, материалом, первой страницей и методом.
Сообщения о регистрации в Telegram также используют сохранённый снимок.

В «Аналитике» блок «Источники аккаунтов и покупки Premium» считает аккаунты,
подтверждённых покупателей и конверсию по источнику/каналу. Есть детализация
кампаний и первых статей. Режим «Регистрации за период» выбирает аккаунты по
дате регистрации; их покупки учитываются до текущего момента. «Всё время»
считает все доступные аккаунты. Продления не увеличивают число покупателей.
Учитывается сохранённое серверное подтверждение оплаты; текущий доступ
сам по себе не доказывает покупку. Истечение Apple/СБП-доступа не удаляет
известную оплату. Для истёкшего или неопределённого состояния Google Play
невозможно отличить обычное окончание от отзыва по одной подписке: такое
подтверждение считается неполным, пока нет другой подтверждённой оплаты.
Ручные выдачи, известные тестовые, бесплатные и возвращённые покупки
исключаются. Для старых или неполных записей показывается нижняя граница
конверсии. Это не полный исторический платёжный журнал: возвраты и статусы
магазинов отражают последнюю доступную серверную проверку. Режим «Всё время»
расширяет набор аккаунтов и не гарантирует полноту их оплат за всю жизнь.

«Источники сайта» — просмотры страниц и попытки перехода по ссылкам; это
события, не уникальные посетители и не подтверждённые установки.
События идут через существующий `trackStats`/`StatsBuffer`; счётчики могут
отставать до 10 минут. Источники аккаунтов читаются из проекций профилей,
которые также могут отставать от подтверждённой записи AccountState.

## Данные и границы хранения

Для атрибуции не вводятся рекламный ID, fingerprint или сопоставление людей
по IP. События сайта передают путь страницы, нормализованные метки и hostname
реферера; полный Referer, поисковая строка, OAuth-код и URL fragment в снимок
не входят. Нативный кеш RuStore также содержит только разрешённые поля;
посторонние параметры магазина отбрасываются. UTM не должны содержать email, имя, номер телефона или другие
персональные значения: использовать идентификаторы кампаний и материалов.
Профиль аккаунта продолжает содержать существующие данные учётной записи;
метки связываются с этим аккаунтом в авторитетном AccountState и его проекциях.

Очистка данных браузера/приложения начинает новый локальный снимок. При
повторном входе сервер сохраняет уже известный источник существующего
аккаунта. Переход на другое устройство или установка из App Store без
прежнего известного аккаунта не создаёт доказанного моста с посещением сайта.

## Активация и проверка

1. Выпустить Worker: приём полей, сохранение снимка, данные админки и CSV.
2. Выпустить лендинг/блог: общий трекер, страницы теста/тарифов и `/go/*/`.
3. Пересобрать и выпустить веб-приложение `/app/`: чтение общего снимка.
4. Выпустить новые Android-сборки Google Play и RuStore. Только они читают
   новый полный контекст, RuStore SDK и категорию органики Google Play.
5. Проверить реальные переходы с отдельными тестовыми кампаниями. Не стирать
   источник рабочего аккаунта ради проверки: использовать отдельный аккаунт
   и чистый профиль браузера/новую установку.

Обновление сайта или Worker не меняет уже установленные старые клиенты.
Исторические пропуски не заполняются автоматически. Выпуск не требует
изменения лимитов ИИ, тарифов или правил выдачи Premium.

```bash
# Из корня main/
node --test tools/blog_admin/test_tracker.cjs
python3 -m unittest tools.blog_admin.test_generator
flutter test test/acquisition_service_test.dart
flutter analyze
flutter test

# Из server/install-notifier/
npm run test:attribution
npm run test:attribution:ui
npm run test:usage
npm run test:logging
npm run test:security
```

# Надёжность входа, покупок и синхронизации — 22.10.2026

Приоритет владельца: корректная работа пользователей важнее экономии до $5.
Этот аудит дополняет [анализ стоимости](../server/cloudflare-costs.md).
Изменения требуют отдельного деплоя Worker и обновления приложения. Проверки
на моделях ошибок и локальном workerd не доказывают отсутствие всех ошибок
в реальных магазинах и сети пользователей.

## Исправления

1. Временная недоступность JWKS/OAuth больше не выдаётся за неверный пароль
   или credential: сервер отвечает 503 с `Retry-After`. Клиент ограниченно
   повторяет именно выдачу сессии; неверная подпись, аудитория, issuer и срок
   по-прежнему дают отказ. Отмена/смена аккаунта останавливает повтор.
2. Каталог запрашивает два точных продукта своего магазина вместо 27
   предполагаемых идентификаторов. Частичный ответ больше не считается полным
   успехом. Перед покупкой заново запрашивается выбранный SKU: устаревший
   `ProductDetails`/offer token не отправляется в оплату. Проверка чека,
   восстановление и привязка покупки к аккаунту не менялись.
3. Чтения AccountState, уведомлений и истории поддержки получили максимум
   три попытки с новым DO stub и короткой экспоненциальной паузой. Повтор
   разрешён только для явно перечисленных чтений, при `retryable === true`
   и без `overloaded`. POST оплаты, начисления, записи прогресса, seed истории
   и отправка уведомлений автоматически не повторяются этим механизмом.
4. Ошибка чтения или повреждённый JSON профиля/прогресса больше не считается
   отсутствующим документом. Sync и покупка прерываются, сохраняя прежние
   данные, вместо записи нового пустого профиля поверх Premium или прогресса.
5. Исправлена совместимость оптимизированного Worker со старым AccountState
   во время выкладки: старый read-many RPC может возвращать `200 ignored`,
   а не 404. Fallback разрешён только для этих явных старых ответов; неверная
   схема и недоступность хранилища не открывают доступ отозванной сессии.
6. Диагностика различает таймаут хранилища, перегрузку и временную ошибку DO.
   Логи содержат ограниченные технические поля и флаги, без текста исключения,
   токенов, URL и содержимого прогресса. Включена загрузка server source maps.
   Для пойманных ошибок остаются безопасные номера строк сборки: source maps
   автоматически расшифровывают прежде всего неперехваченные исключения.

Повторы и безопасное обновление деталей магазина соответствуют рекомендациям
[Cloudflare](https://developers.cloudflare.com/durable-objects/best-practices/error-handling/)
и [Google Billing](https://developer.android.com/google/play/billing/integrate).
Настройка source maps — по [документации Cloudflare](https://developers.cloudflare.com/workers/observability/source-maps/).

## Практический выбор средств наблюдения

### Ограничения интернета в России

Часть `network_error` и таймаутов может быть вызвана доступностью внешних
сервисов из российских сетей. Cloudflare [сообщала 26.06.2025](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet)
об ограничениях со стороны российских провайдеров: обрывах, таймаутах и
передаче только первых 16 КБ. Это свидетельство риска маршрута, а не
доказательство причины каждой ошибки пользователей за 21–22.10.2026.

`BackendConfig` использует `workers.dev` и `api.pdd-drive.app` одного Worker.
Разные домены могут помочь при проблеме конкретного имени/маршрута, но оба
зависят от Cloudflare. Они не защищают от общего ограничения сети Cloudflare.
Сбой внутреннего DO storage также не устраняется заменой клиентского домена.

Перед инфраструктурным переносом измерить доступность обоих адресов из
нескольких российских мобильных и домашних сетей: DNS/TLS/таймауты, небольшой
и большой ответ, успешность входа и синхронизации. Сравнить с сетью вне России.
Не использовать страну IP как доказательство блокировки или платёжного региона.

Если ограничение подтверждено, следующий вариант — независимая HTTPS-точка
входа вне сети Cloudflare с проверенным маршрутом к единственному хранилищу
аккаунтов. Это может быть reverse proxy; полноценный перенос backend сложнее.
Не создавать две независимо изменяемые базы профилей/Premium и не повторять
финансовые POST через оба адреса без идемпотентности. Сначала staging и проверки
покупок/прогресса; затем согласованное переключение. Новый хостинг в этом аудите
не создавался. Ограничения магазинов и внешних OAuth SDK требуют отдельных
проверок и не исчезнут автоматически после переноса нашего API.

### Системы диагностики

| Решение | Где полезно | Решение для проекта |
| --- | --- | --- |
| Cloudflare Logs + source maps | Worker, исключения DO, версия сервера | Оставить и улучшить технические коды уже сейчас |
| Firebase Crashlytics | Flutter Android/iOS, native crashes, non-fatal и ANR | Предпочтительный следующий шаг для мобильного приложения: Firebase уже подключён |
| Sentry Flutter + Workers | Единая диагностика клиента, web и сервера, связь ошибок и трасс | Альтернатива, если нужен единый сервис; проверить совместимость и стоимость до внедрения |
| Telegram | Быстро узнать об инциденте | Оставить уведомления; не использовать число сообщений как показатель качества |

Crashlytics требует подключения плагина, конфигурации сборок, загрузки символов
и подтверждения тестового события в консоли, а не только добавления зависимости:
[официальный порядок](https://firebase.google.com/docs/crashlytics/flutter/get-started).
SDK не подключён скрыто в рамках аудита; сначала проверить совместимость ОС,
сборки и перечень отправляемых данных. Crashlytics не заменяет журнал web/Worker.

Нельзя просто обновить Sentry до текущего major 10: он требует Android API 26,
Dart 3.12 и Flutter 3.44, тогда как текущая сборка использует Android API 24.
Такое изменение исключит часть пользователей. Нужна совместимая версия или
отдельное продуктовое решение о поддержке ОС. Источник: [changelog SDK](https://pub.dev/packages/sentry_flutter/versions/10.0.0/changelog).

Долгосрочно важнее инструмента:

- Считать долю успешных входов, загрузок каталога и sync по версии/магазину
  и платформе; отделять фоновые попытки от ошибки на экране покупки.
- Проверять offline/online, потерянный ответ после commit, повтор callback,
  смену аккаунта, два устройства, восстановление покупки и перезапуск DO.
- Для progress POST ввести request ID и дедуп в той же транзакции, что прогресс.
  Повтор старого снимка после потерянного ответа может затереть более новые
  настройки второго устройства. Сейчас серверный retry записи не расширен;
  существующий сетевой retry клиента не даёт полной exactly-once гарантии.
- Google Android в перспективе перевести на подписанный ID token, предварительно
  сверив OAuth-проекты и SHA-1. Слепая смена `serverClientId` способна сломать вход:
  [проверка личности на backend](https://developers.google.com/identity/sign-in/android/backend-auth).
- Развивать тесты в настоящем workerd наряду с быстрыми Map-fixtures:
  [Cloudflare testing](https://developers.cloudflare.com/workers/testing/vitest-integration/).

## Условия выпуска и сохранности

Итоговая проверка изменения:

- `flutter analyze` — без замечаний; `flutter test` — 723 passed, 3 skipped.
- `npm test` — успешно; `node --test test-*.mjs` — 410 passed, 1 skipped
  (локальный runtime намеренно opt-in).
- `npm run test:security` — 200 passed, включая совместимость старого DO,
  искусственные I/O/JSON/commit/lost-response сбои и сохранность Premium.
- `RUN_RUNTIME_SMOKE=1 npm run test:runtime` — 1 passed: настоящий workerd,
  SQLite DO, Unicode progress >128 КиБ, немедленная проекция KV, четыре старта
  процесса, отзыв/удаление сессий и одноразовый импорт поддержки.
- `wrangler deploy --dry-run` — сборка успешна; это не production-деплой.

Сохранение изменённого прогресса и финансовых данных остаётся немедленным.
Отзыв сессии проверяется без кэша. Экономия меняет только административную
свежесть lastSeenAt (до 5 минут) и проверку флага webhook (до минуты); сообщения
поддержки не кэшируются. Жёсткого отключения сервера при достижении $5 нет.

До production: все Flutter/Node проверки, локальный workerd smoke, сухая сборка
Worker, резервная копия и согласование по [правилам rollout](../premium/account-state-rollout.md).
После согласованного деплоя: проверить старые Android/iOS клиенты, статус уже
оплаченного Premium, sync между устройствами, поддержку и выход/удаление.
Мобильные исправления каталога и повтора входа требуют отдельного обновления
приложения. Перед его отправкой обязательны реальные проверки магазинов.

После выпуска сравнивать успешность и задержки с исходным периодом; при
регрессии остановить расширение выпуска. Цель — меньше пользовательских
отказов и сохранные данные, а не только меньше строк в Telegram или ровно $5.

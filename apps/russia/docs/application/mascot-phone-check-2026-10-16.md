Улучшение повторного запуска нельзя приписывать только правке интерфейса:
ресурсы и драйвер после первых проходов уже прогреты. На первом запуске Godot
остаются отдельные пики около 90 мс; обещания полного отсутствия пропусков кадров нет.
Продолжительных застываний маскота в записи не обнаружено. Переход на игру происходит
по факту готового отрисованного кадра. Подготовка не продлевается ради анимации.

Холодный старт финальной Activity: Android `am start -W` — `TotalTime=326` мс.
Это время первого отображения Activity, а не отдельный замер полной готовности всех
сервисов. Flutter startup gate виден недолго (примерно 0,1–0,17 с на этом телефоне),
поэтому его 3–7 кадров недостаточно для устойчивой оценки p95. На первых кадрах
Flutter/главного экрана также встречаются разовые raster-пики до 50–67 мс.

## Поведение и исправления после телефона

- Холодный запуск, город, обе Godot-мини-игры, повторный вход и возврат работают.
- Отмена загрузки системным Back возвращает меню через безопасный `Host.exit`;
  игровой процесс после выхода не остаётся запущенным.
- Светлая и тёмная темы проверены. Исходная светлая тема восстановлена.
- Устранены тёмная starting-window вспышка и движение поверхности на входе.
  Системные значки читаемы на светлой и тёмной подложке маскота.
- На фоне игры скрытый загрузчик не продолжает анимироваться. Файлы не распаковываются
  в массив всех кадров. Для штатной сборки диагностические подписки отключены.
- На Android API 24–27 нативное покрытие игры использует постер; Flutter WebP работает
  через штатный кодек. Эта ветка на старом телефоне не измерялась.
